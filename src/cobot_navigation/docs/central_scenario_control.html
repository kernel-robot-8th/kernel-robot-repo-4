위 명령은 fleet_control이 이미 실행 중인 경우입니다. 아직 실행하지 않았다면 fleet:=start로 바꿉니다. 브라우저 접속 주소는 http://127.0.0.1:8080입니다. mode:=execute는 서버를 실제로 시작하며, 로봇 작업 허용은 화면에서 따로 켜야 합니다. mode를 생략하면 파일·서버를 시작하지 않는 미리보기입니다.

기존 웹 화면·API·상태 수집기를 재사용하고 작업 실행기는 fleet으로 교체합니다. 이 기동기는 기존 fleet_status_node와 fleet_api_node를 시작하며 task_manager_node는 시작하지 않습니다. API launch가 없는 옛 control-center 패키지는 기동 전에 거절합니다. 현재 브랜치에 없는 웹 소스를 자동 병합하지 않으므로 아래 별도 빌드가 필요합니다.

source는 현재 터미널에 프로그램 위치를 알려주는 명령입니다. install/setup.bash로 기존 프로젝트와 기반 환경을 불러온 뒤, install/control_center_web/local_setup.bash로 별도 빌드한 웹 패키지를 추가합니다. 웹 쪽을 나중에 불러와야 웹 기능이 있는 cobot_control_center가 우선 선택됩니다. 새 터미널에서는 이 순서를 다시 적용합니다. setup.bash는 빌드할 때 연결된 기반 환경도 함께 불러오고, local_setup.bash는 해당 설치 경로만 추가합니다.

관제 PC에서 전체 주문을 접수하는 명령

Docker 서비스가 실행된 상태에서 사용합니다. 상품·수량·경로는 실제 현장 값으로 바꿉니다. 예시는 SHOE42의 가용 재고가 2개인 경우입니다. 재고를 등록한 뒤 주문을 접수하고, 현장 준비와 접수 응답을 확인한 후 웹에서 작업 명령 켜기를 누릅니다. 이미 가동 허용이 켜져 있으면 준비된 주문은 접수 후 실행될 수 있습니다.

별도 터미널: 관제의 처리 응답을 먼저 관찰
docker exec -it cobot-fleet-fleet-1 /opt/cobot/entrypoint.sh \
  ros2 topic echo /control_center/task_events std_msgs/msg/String
1. 예약분을 제외한 가용 재고를 절대값으로 등록
docker exec cobot-fleet-fleet-1 /opt/cobot/entrypoint.sh \
  ros2 topic pub --once /control_center/task_request std_msgs/msg/String \
  '{data: "{\"type\":\"inventory\",\"request_id\":\"stock-001\",\"sku\":\"SHOE42\",\"available\":2}"}'

request_id=stock-001의 reply.status=200을 확인합니다. available=2는 2개를 더하는 요청이 아니라 가용 수량을 2개로 설정하는 요청입니다. 주문 접수 후 같은 재고 등록을 반복하면 가용 수량을 다시 설정하므로 실제 재고를 확인해야 합니다.

2. 전체 주문 접수 — ZA 상차 → ZC 하차 → HOME
docker exec cobot-fleet-fleet-1 /opt/cobot/entrypoint.sh \
  ros2 topic pub --once /control_center/task_request std_msgs/msg/String \
  '{data: "{\"type\":\"order\",\"request_id\":\"submit-001\",\"order\":{\"order_id\":\"order-001\",\"sku\":\"SHOE42\",\"quantity\":1,\"route\":\"lab_delivery\"}}"}'

request_id=submit-001의 reply.status=202와 주문 내용을 확인합니다. 재고 부족·필드 오류는 거절됩니다. 같은 order_id와 동일 내용의 재전송은 기존 주문을 반환하며, 새로운 주문에는 새로운 주문 ID를 사용합니다.

3. 전체 주문의 현재 단계와 배정 로봇 조회
docker exec cobot-fleet-fleet-1 /opt/cobot/entrypoint.sh \
  ros2 topic echo /control_center/tasks std_msgs/msg/String \
  --qos-durability transient_local --once

orders의 order_id, robot_id, state, stage, request_id, detail을 확인합니다. 작업 명령이 꺼져 있거나 배정 조건이 충족되지 않으면 WAITING으로 남습니다. 웹의 /api/tasks는 개별 주행 목록이므로 전체 주문 확인에는 위 스냅샷이나 실시간 BT 조회 도구를 사용합니다.

04. 기존 로직에서 바꾼 점

통신 타임아웃은 “끝났다”가 아닙니다

  • 주행·팔 작업의 결과가 불명확하면 UNKNOWN으로 두고 예약을 유지합니다.
  • 관제 재시작은 자동 명령 재전송을 하지 않습니다.
  • 로봇도 관제 하트비트 단절을 감시하고 정지 래치를 유지합니다.
  • 링크 회복만으로 해제하지 않습니다. 운영자 복구와 control_reset 반향이 필요합니다.

시간 경과로 구역을 비우지 않습니다

  • zone_manager의 max_hold_sec 경과는 경고만 발생시킵니다.
  • 통로·작업 구역 점유는 실제 이탈이나 현장 정리 확인 뒤 해제합니다.
  • 운반 도착과 공유 통로의 후미 이탈은 다른 증거로 받습니다.
  • 팔 동작 중 로봇이 스스로 복귀하지 않도록 중앙 모드에서 유휴 복귀를 끕니다.
시나리오에서 보수적으로 바꾼 분기. 전체 비상정지 해제 직후 전 로봇을 자동 HOME으로 보내지 않습니다. 상하차 도중 중단한 물리 작업은 확인 없이 이어서 피킹하지 않습니다. 적재 후 정차 실패·상품 불일치·화물 불명은 UNKNOWN으로 남깁니다. 운영자가 안전·화물·자원을 확인한 후 재개 가능한 주행 단계만 새 요청 ID로 재개합니다.

공통 작업 구역을 쓰는 배송·반품은 출발 전에 양쪽 작업 자원을 묶어서 예약합니다. 반대 방향 주문이 서로의 구역을 기다리는 교착을 막는 보수적인 정책이며, 동일 경로의 처리량보다 안전한 순차 처리를 우선합니다. 별도 작업 구역의 주문은 병행할 수 있습니다.

이 JSON 세션 가드는 지연·중복 방지용입니다. 인증·서명, 하드웨어 비상정지, 실시간 안전 제어의 대체물이 아닙니다. 팔·비전 어댑터도 자체 워치독·작업 ID 중복 방지·유효시간 검사가 필요합니다.

장치 결과의 최소 증거
  • 공통: 해당 request_id / order_id / robot_id / stage / source 일치, measured=true, finished=true, success는 bool.
  • DOCK_*: data.xy_m, yaw_deg는 유한 실측값. 공차 이내이며 stopped=true, base_hold=true여야 진행.
  • MARKER / QR: data.sku가 주문 상품과 일치해야 진행.
  • VERIFY_LOAD: load_present=true, arm_safe=true.
  • VERIFY_UNLOAD: placed=true, load_absent=true, arm_safe=true.
  • PICKUP_EXIT / PATH_EXIT / RETURN_EXIT: clear=true로 실제 공유 통로 이탈 확인.
  • 실패 재시도: success=false이면서 data.retry_safe=true가 있어야 재시도. 파손·낙하·실행 여부 불명은 안전한 재시도로 응답하면 안 됩니다.
  • 각 어댑터는 현재 /fleet/heartbeat 세션, 증가 seq, issued_at/ttl_sec를 검사하고 request_id를 영속 중복 제거해야 합니다. ACK만으로 finished=true를 만들지 않습니다.

활성 주문이 없는 로봇의 정지 래치·수동 제어권은 release_control 요청에 robot_id, operator, note, 같은 evidence를 담아 반환합니다. 반환 뒤에도 arm 요청이 필요합니다.

06. 현장 실행 순서

현재 기본값. 관제 도메인 100, 로봇 10/20/30은 기존 설정을 유지했습니다. lab_delivery는 ZA→ZC, lab_delivery_zb는 ZB→ZC입니다. 두 경로 모두 상차 omx1·하차 omx2를 사용하며, 장치 어댑터를 연결해야 합니다. 지도 좌표는 기존 lab.yaml을 재사용하며 새 좌표를 만들지 않았습니다.
  1. control-center의 웹·fleet_status는 유지하고, 직접 patrol_cmd를 발행하는 task_manager_node는 중지합니다. 기존 통합 bringup이 이를 다시 띄우지 않게 구성해야 합니다.
  2. 로봇에는 갱신된 patrol과 central_guard를 함께 배포합니다. 중앙 PC에는 갱신된 fleet·bridge·zone_manager를 배포합니다. 로봇과 관제 PC의 시계를 동기화합니다.
  3. 로봇의 central_controlled=true를 사용합니다. 독립 주행 점검에서만 false로 설정하고 중앙 실행기는 함께 사용하지 않습니다.
  4. bridge → zone_manager → patrol → fleet 순서로 실행합니다. 팔·비전·보정 어댑터는 관제 도메인에서 work_request / result에 연결합니다.
  5. 통신·배터리·지도·작업 구역을 확인하고 웹에서 작업 명령을 켭니다. 재고를 등록한 뒤 주문을 접수합니다.

07. 어떤 코드가 어떻게 실행되는가

전체 시나리오는 실제 py_trees 트리로 실행합니다. scenario.py의 단계 전이표와 거대한 성공 분기는 제거했습니다. 업무 순서는 scenario_tree.py에서 한눈에 읽을 수 있습니다.

실제 코드 호출 흐름도

두 흐름을 전환해 확인하세요. 파일 이름이 있는 카드를 누르면 해당 소스가 열립니다. 모바일에서는 도표 안을 좌우로 스크롤할 수 있습니다.

요청·실행타이머·결과·관측외부 어댑터 연결 필요

실선은 현재 코드의 호출·데이터 경로입니다. 주문용 웹 입력과 외부 추론 PC 어댑터의 연결 상태는 별도로 표시했습니다. 실시간 BT 상태는 조회 도구에서 확인하며, 이 도표는 정상 업무의 코드 구조 설명입니다. 정지·복구 조건과 보조 기동 코드의 역할은 아래 상세 설명을 참고하세요.

① 개별 이동 버튼

POST /api/tasks → 기존 fleet_api → type=create → ControlAPI._create() → FleetService.submit() → 주행 BT. 주문 전체 업무를 시작하는 버튼은 아닙니다.

② 주문 전체 업무

type=order → ScenarioService.submit() → 재고 예약·WAITING 저장 → 로봇 배정 → 주문별 전체 BT. 기존 웹에는 주문용 HTTP 경로와 화면 연결을 추가해야 합니다.

순차 노드는 완료한 자식을 기억합니다. 작업 허용만 껐다 켜면 실행 위치를 보존하고, 정지·수동 전환·통신 단절은 트리를 무효화합니다. 운영자 복구는 이동·수령 체크포인트에서 새 트리를 만들며 이미 수행한 물리 피킹을 다시 실행하지 않습니다.

주행 단계는 하위 BT와 실제 로봇 결과까지 확인합니다

NavigationStep → ScenarioContext.dispatch() → FleetService.submit()이 Dispatch → AwaitResult 트리를 만듭니다. Dispatch가 patrol_cmd를 한 번 보내고, AwaitResult가 동일 command_id와 task_finished=true를 확인합니다. 주행 BT의 SUCCEEDED를 주문 BT가 읽어야 다음 노드가 열립니다.

명령을 ROS에 발행한 사실만으로 도착을 확정하지 않습니다. 주행 결과 불명·시간 초과는 UNKNOWN과 예약 유지로 이어집니다.

팔·비전 단계는 별도 장치 결과를 기다립니다

DeviceStep → ScenarioContext.dispatch() → FleetControlNode.work() → /fleet/work_request로 전달합니다. 별도 장치 어댑터의 /fleet/work_result를 받아 주문·로봇·단계·출처·request_id·실측·종료 여부를 모두 맞춘 뒤 해당 BT 노드에 전달합니다.

결과 콜백에서는 트리 상태만 정리하고 다음 물리 명령을 보내지 않습니다. 새 명령은 다음 타이머에서 전달합니다. 상하차 추론 PC의 원격 HTTP API·실행 어댑터는 아직 연결되지 않았습니다. ACT 한 번이 전체 피킹·배치를 수행하는 경우 논리 단계와 실제 모델 호출을 중복 없이 대응시키는 어댑터가 필요합니다.

재시도·실패·복구는 어떤 조건에서 동작하나요?
  • 실측 종료 결과가 실패이며 retry_safe=true일 때만 SafeRetry가 다시 실행합니다. 전송 예외·시간 초과·결과 불명은 자동 재시도하지 않습니다.
  • 적재 검증 실패는 LOAD부터, 배치 검증 실패는 UNLOAD부터 공유 예산으로 재시도합니다. 과거 request_id의 결과는 버립니다.
  • 정차 공차가 벗어나면 보정 → 새 실측을 반복합니다. 피킹 전 상차 정차 실패만 HOME 복귀를 허용하고, 화물 작업 중 실패는 보류합니다.
  • scenario_safety.py가 중단 시 시도 무효화·정지·예약 보류를 수행합니다. 재시작은 미종료 주문을 UNKNOWN으로 바꾸며 자동 전송하지 않습니다.
  • 수령 입력 또는 제한 시간 후 복귀를 진행합니다. 무응답 복귀를 실제 수령으로 기록하지 않습니다.
