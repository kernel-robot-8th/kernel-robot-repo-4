01. 역할과 명령 경계를 분리했습니다

비교 기준: feature/control-center · b847b8e · 2026-11-03. 해당 브랜치의 파일을 덮어쓰거나 병합하지 않았습니다.

웹·API·화면

cobot_control_center

HTTP/WebSocket, 카메라, 화면용 상태 집계는 기존 관제 구현을 사용합니다. fleet에 웹 서버나 MQTT 접수기를 다시 두지 않습니다.

중앙 시나리오

cobot_fleet_control

재고 예약, 배정, 출발 간격, 구역·팔·통로 예약, 작업 단계, 증거 판정, 재시도, 수령, 복귀와 복구를 소유합니다.

장치별 실제 동작

patrol / Nav2 / 팔·비전 어댑터

주행은 기존 patrol·Nav2에 위임합니다. 팔·비전·정밀 정차는 요청을 받아 실제 작업을 수행하고 측정 결과를 반환해야 합니다.

Web / APItask_request → 요청
→
Fleet executor시나리오 + 주행 BT + 실행 원장
→
Domain bridge100 ↔ 10 / 20 / 30
→
Pinkypatrol → Nav2
상태·실제 종료 → 중앙
명령 발행자는 하나만 실행합니다. 기존 control-center의 task_manager_node와 새 fleet_control_node를 동시에 켜면 안 됩니다. 웹 API·상태 수집기는 유지하고 작업 실행기만 fleet으로 교체합니다. 중앙은 중복 patrol_cmd 발행자를 감지하면 주행 전달을 거절합니다. 이 검사는 인증이나 완전한 분산 리더 선출을 대신하지 않습니다.

04. 기존 로직에서 바꾼 점

통신 타임아웃은 “끝났다”가 아닙니다

  • 주행·팔 작업의 결과가 불명확하면 UNKNOWN으로 두고 예약을 유지합니다.
  • 관제 재시작은 자동 명령 재전송을 하지 않습니다.
  • 로봇도 관제 하트비트 단절을 감시하고 정지 래치를 유지합니다.
  • 링크 회복만으로 해제하지 않습니다. 운영자 복구와 control_reset 반향이 필요합니다.

시간 경과로 구역을 비우지 않습니다

  • zone_manager의 max_hold_sec 경과는 경고만 발생시킵니다.
  • 통로·작업 구역 점유는 실제 이탈이나 현장 정리 확인 뒤 해제합니다.
  • 운반 도착과 공유 통로의 후미 이탈은 다른 증거로 받습니다.
  • 팔 동작 중 로봇이 스스로 복귀하지 않도록 중앙 모드에서 유휴 복귀를 끕니다.
시나리오에서 보수적으로 바꾼 분기. 전체 비상정지 해제 직후 전 로봇을 자동 HOME으로 보내지 않습니다. 상하차 도중 중단한 물리 작업은 확인 없이 이어서 피킹하지 않습니다. 적재 후 정차 실패·상품 불일치·화물 불명은 UNKNOWN으로 남깁니다. 운영자가 안전·화물·자원을 확인한 후 재개 가능한 주행 단계만 새 요청 ID로 재개합니다.

공통 작업 구역을 쓰는 배송·반품은 출발 전에 양쪽 작업 자원을 묶어서 예약합니다. 반대 방향 주문이 서로의 구역을 기다리는 교착을 막는 보수적인 정책이며, 동일 경로의 처리량보다 안전한 순차 처리를 우선합니다. 별도 작업 구역의 주문은 병행할 수 있습니다.

이 JSON 세션 가드는 지연·중복 방지용입니다. 인증·서명, 하드웨어 비상정지, 실시간 안전 제어의 대체물이 아닙니다. 팔·비전 어댑터도 자체 워치독·작업 ID 중복 방지·유효시간 검사가 필요합니다.

마커 인식 결과 예시 (장치 어댑터가 발행)
{
  "order_id": "order-001", "robot_id": "pinky1",
  "request_id": "해당_work_request의_ID",
  "stage": "MARKER", "source": "vision",
  "measured": true, "finished": true,
  "success": true,
  "data": {"sku": "SHOE42"}
}
장치 결과의 최소 증거
  • 공통: 해당 request_id / order_id / robot_id / stage / source 일치, measured=true, finished=true, success는 bool.
  • DOCK_*: data.xy_m, yaw_deg는 유한 실측값. 공차 이내이며 stopped=true, base_hold=true여야 진행.
  • MARKER / QR: data.sku가 주문 상품과 일치해야 진행.
  • VERIFY_LOAD: load_present=true, arm_safe=true.
  • VERIFY_UNLOAD: placed=true, load_absent=true, arm_safe=true.
  • PICKUP_EXIT / PATH_EXIT / RETURN_EXIT: clear=true로 실제 공유 통로 이탈 확인.
  • 실패 재시도: success=false이면서 data.retry_safe=true가 있어야 재시도. 파손·낙하·실행 여부 불명은 안전한 재시도로 응답하면 안 됩니다.
  • 각 어댑터는 현재 /fleet/heartbeat 세션, 증가 seq, issued_at/ttl_sec를 검사하고 request_id를 영속 중복 제거해야 합니다. ACK만으로 finished=true를 만들지 않습니다.
워크 요청 예시와 가능한 action
{
  "request_id": "단계마다_새_UUID", "order_id": "order-001",
  "robot_id": "pinky1", "stage": "LOAD", "target": "omx1",
  "action": "load", "sku": "SHOE42", "quantity": 1,
  "attempt": 1, "timeout_sec": 300.0,
  "route": {"pickup":"ZA","dropoff":"ZB","pickup_arm":"omx1","dropoff_arm":"omx2","lane":"main"},
  "session_id": "현재_관제_세션", "seq": 3,
  "issued_at": 1793790000.0, "ttl_sec": 5.0
}

action: dock_check, dock_correct, marker, qr, pick, load, unload, verify_load, verify_unload, path_exit, warehouse_store, hold, release_hold. release_hold는 운영자 확인 후의 정지 유지 해제 요청이며 새 팔 모션을 시작하지 않습니다. hold는 중앙의 소프트 정지 요청이며 물리 안전 정지 완료와 다릅니다. 모든 장치에서 실제 stop 피드백과 로컬 통신 감시를 구현해야 합니다.

운영자 복구와 수령 확인
{"type":"received","request_id":"receipt-1","order_id":"order-001"}

{
  "type":"resolve", "request_id":"recover-1", "order_id":"order-001",
  "operator":"operator1", "note":"현장 정지·팔 퇴피·화물·구역 확인",
  "decision":"resume",
  "evidence": {
    "base_stopped":true, "arms_safe":true,
    "cargo_reconciled":true, "resources_clear":true
  }
}

resume은 MOVE_PICKUP / MOVE_DROPOFF / RETURN_HOME / CUSTOMER에만 허용합니다. 팔·피킹 중간 상태는 fail로 정리하고 새 주문을 생성합니다. 여기의 evidence는 운영자 확인 기록이며 센서 측정을 대신하지 않습니다. 실제 확인 없이 true로 채우면 안 됩니다.

활성 주문이 없는 로봇의 정지 래치·수동 제어권은 release_control 요청에 robot_id, operator, note, 같은 evidence를 담아 반환합니다. 반환 뒤에도 arm 요청이 필요합니다.

06. 현장 실행 순서

현재 기본값. 관제 도메인 100, 로봇 10/20/30은 기존 설정을 유지했습니다. lab_delivery의 ZA→ZB 및 omx1/omx2 연결은 예시 매핑입니다. 실제 작업 구역·팔 ID를 scenario.yaml에 맞추고 장치 어댑터를 연결해야 합니다. 지도 좌표는 기존 lab.yaml을 재사용하며 새 좌표를 만들지 않았습니다.
  1. control-center의 웹·fleet_status는 유지하고, 직접 patrol_cmd를 발행하는 task_manager_node는 중지합니다. 기존 통합 bringup이 이를 다시 띄우지 않게 구성해야 합니다.
  2. 로봇에는 갱신된 patrol과 central_guard를 함께 배포합니다. 중앙 PC에는 갱신된 fleet·bridge·zone_manager를 배포합니다. 로봇과 관제 PC의 시계를 동기화합니다.
  3. 로봇의 central_controlled=true를 사용합니다. 독립 주행 점검에서만 false로 설정하고 중앙 실행기는 함께 사용하지 않습니다.
  4. bridge → zone_manager → patrol → fleet 순서로 실행합니다. 팔·비전·보정 어댑터는 관제 도메인에서 work_request / result에 연결합니다.
  5. 통신·배터리·지도·작업 구역을 확인하고 웹에서 작업 명령을 켭니다. 재고를 등록한 뒤 주문을 접수합니다.
빌드 (각 장치의 기존 ROS / vendor underlay를 먼저 source)
# 관제 PC
colcon build --packages-select cobot_fleet_control cobot_domain_bridge cobot_zone_traffic_control
source install/setup.bash
# 로봇
colcon build --packages-select cobot_pinky_patrol cobot_zone_traffic_control
source install/setup.bash
Linux 관제 PC · 기존 설정을 사용하는 수동 기동
export ROS_DOMAIN_ID=100
ros2 launch cobot_domain_bridge bridges.launch.xml
# 별도 터미널
ros2 launch cobot_zone_traffic_control zone_manager.launch.xml
# 별도 터미널: 기본 작업 명령 꺼짐
ros2 launch cobot_fleet_control fleet_control.launch.xml

기존 fleet_startup.launch.xml의 SSH 순차 기동도 유지합니다. 계정과 장치 설정을 채운 후 사용합니다. Docker에는 fleet·bridge·zone-manager만 남겼으며 MQTT 브로커와 Paho 의존성은 제거했습니다.

웹 백엔드에서 전달할 준비 요청 예시
{"type":"inventory","request_id":"stock1","sku":"SHOE42","available":5}
{"type":"arm","request_id":"arm1","armed":true,"source":"operator1"}

available은 예약분을 제외한 가용 수량의 절대값입니다. 실패한 주문의 화물·재고를 확인하기 전에는 재고를 자동 복원하지 않습니다. 기존 웹의 단일 명령 create / arm / stop 응답 형식은 유지했지만, 주문 카드·수령·복구·새 이벤트 화면은 웹 담당의 연결 작업이 필요합니다. raw 명령은 제거했습니다.
