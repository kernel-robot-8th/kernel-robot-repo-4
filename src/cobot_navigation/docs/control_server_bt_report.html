뒤 파일에서 같은 파라미터를 지정하면 그 값이 우선합니다. 기존 로봇별 launch 이름은 공통 launch를 호출하고, 실행 이름은 같은 Python 진입점의 별칭입니다.

YAML 맨 위 이름은 ROS 노드 이름

pinky_patrol_node:
  ros__parameters:
    robot_id: pinky1
    home_name: I1

pinky_patrol_node:는 Python 파일명이나 클래스명이 아닙니다. launch의 노드 이름과 대응하고 Python이 get_parameter()로 값을 읽습니다.

예전 config/pinky1.yaml 한 파일은 세 계층으로 분리되었습니다. 미사용 예비 원점 지점 P36~P50은 제거했으며 실제 좌표를 등록하기 전에는 unknown point로 거절됩니다. 설정 수정 뒤 해당 장비에 재빌드·배포하고 노드를 다시 시작합니다.

04 / 처음 설치부터 첫 작업까지

통합 기동을 사용하는 실행 순서

  1. 각 로봇에 새 실행기를 배포·빌드

    각 Pinky 터미널 · 최초 배포 / 코드 변경 후

    사용 중인 vendor ROS 환경을 불러온 뒤 실행합니다. 같은 코드와 현장 설정을 세 로봇에 배포합니다.

    cd /ws/kernel-robot-repo-4
source /opt/ros/jazzy/setup.bash
# 별도 vendor workspace가 있다면 해당 install/setup.bash도 source
colcon build --packages-select cobot_zone_traffic_control cobot_pinky_patrol
source install/setup.bash

    로봇 HOME에 cobot_map_v9.yaml과 그 YAML의 image:가 가리키는 파일을 준비합니다. 실제 로봇에 pinky_bringup·pinky_navigation·pinky_interfaces·pinky_led가 있어야 합니다.

  2. 관제 PC 설치·빌드와 MQTT 브로커 준비

    관제 PC의 workspace 최상위 · 최초 설치 / 코드 변경 후
    source /opt/ros/jazzy/setup.bash
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
python -m pip install 'py_trees==2.2.3' 'paho-mqtt==2.1.0'
python "$(command -v colcon)" build --packages-select \
  cobot_fleet_control cobot_zone_traffic_control cobot_domain_bridge
source install/setup.bash
export ROS_DOMAIN_ID=100

    가상환경이 이미 있으면 재사용합니다. colcon은 기존 ROS 빌드 환경에 설치되어 있어야 합니다. 가상환경의 Python으로 colcon 스크립트를 실행해 새 실행기의 Python 환경도 맞춥니다.

    기존 MQTT 브로커가 있으면 그대로 사용합니다. 관제 PC의 기본 주소 localhost:1883에서 개발용 브로커를 별도 터미널로 실행할 때는 다음 명령을 사용합니다.

    mosquitto -p 1883 -v

    통합 기동기는 MQTT 브로커를 시작하지 않습니다. 외부 브로커를 쓴다면 fleet_control.yaml의 주소·포트와 인증 환경변수를 맞춥니다.

  3. SSH와 로봇 환경을 설정

    관제 PC · config/fleet_startup.yaml

    각 ssh_user를 실제 계정으로 채웁니다. vendor 설치 위치는 underlay_setups, 장비에서 쓰는 DDS 값은 environment에 설정합니다. SSH는 대화형 터미널의 .bashrc를 자동 적용하지 않습니다.

    defaults:
  workspace: /ws/kernel-robot-repo-4
  map: ~/cobot_map_v9.yaml
  stage_delay_sec: 5.0
  stage_timeout_sec: 90.0
  underlay_setups: []
  environment: {}
robots:
  pinky1:
    host: 192.168.45.21
    ssh_user: ''  # 실제 SSH 계정 입력 필요
    domain_id: 10

    위는 일부 항목만 발췌한 예시입니다. 기존 pinky2·3 설정도 유지합니다. 키 인증과 사전에 확인·등록된 호스트 키를 사용하며 비밀번호나 개인키 본문은 YAML에 넣지 않습니다.

    소스 YAML을 수정했다면 재빌드·source합니다. launch는 설치된 파일을 읽습니다. 별도 설정 파일을 사용할 때는 미리보기와 실제 기동 모두 config:=/절대/경로/fleet_startup.yaml을 추가합니다.

  4. 관제에서 미리보기 → 실제 기동

    관제 PC 터미널 · 로봇 전원과 네트워크 연결 후
    # 접속·ROS 프로세스 기동 없이 설정과 명령 확인
ros2 launch cobot_fleet_control fleet_startup.launch.xml

# SSH 설정을 완료한 뒤 실제 프로세스 시작
ros2 launch cobot_fleet_control fleet_startup.launch.xml execute:=true

    로봇마다 bringup·Nav2·patrol 준비 검사 로그가 나오고, 마지막에 전체 로봇 기동 검사 완료. SSH 세션을 유지합니다.가 표시됩니다. 이 문구는 기동 검사 완료이며 MQTT 업무 서버의 접속·작업 성공까지 확인한 것은 아닙니다.

    터미널과 SSH 세션을 유지합니다. Ctrl+C는 이 기동기가 시작한 서비스와 원격 세션을 역순 정리합니다. 수동 bringup·Nav2·패트롤이나 기존 관제/Docker 서비스와 중복 실행하지 않습니다.

  5. 결과를 구독하고 이동 작업 전송

    관제 PC · 아래 발행은 실제 이동 요청
    # 모니터 터미널
mosquitto_sub -h localhost -p 1883 -q 1 -v \
  -t 'cobot/fleet/receipts' -t 'cobot/fleet/events'
    # 별도 요청 터미널 · 새 작업에는 새 command_id 사용
mosquitto_pub -h localhost -p 1883 -q 1 \
  -t 'cobot/fleet/commands' \
  -m '{"command_id":"job-run-001","robot_id":"pinky1","operation":"goto","points":["P1"],"timeout_sec":300}'

    현재 UI 버튼의 MQTT 연결은 후속 구현입니다. 작업 상태는 ACCEPTED → RUNNING → SUCCEEDED / FAILED / UNKNOWN으로 확인합니다. 같은 요청의 재전송은 같은 ID를 쓰고 retain은 사용하지 않습니다.

  6. BT 기록을 내보내 HTML에서 재생

    관제 PC → 이 문서의 BT 기록 재생
    ros2 run cobot_fleet_control fleet_bt_trace \
  --db ~/.cobot/fleet_control.sqlite3 \
  --command-id job-run-001 --output /tmp/bt_trace.json

    BT 기록 재생에서 JSON 파일을 선택합니다. 처음 보이는 기본 이력은 가짜 로봇의 격리 실행 기록입니다. 새 기록은 다시 내보내고 선택해야 반영됩니다.

수동으로 켜거나 로봇 한 대만 점검할 때

통합 기동과 택일하는 경로입니다. 로봇에서 ROS·vendor·/ws/kernel-robot-repo-4/install/setup.bash를 source한 뒤 아래 하나로 로컬 단계 기동을 할 수 있습니다.

# 로봇 pinky1에서 실제 순차 기동

06 / 실행 중 자주 묻는 내용

증상에서 확인 위치로 바로 이동

launch를 켰는데 robot_startup.py가 실행되지 않아요

기본은 미리보기입니다. execute:=true에서 SSH가 연결된 뒤 로봇의 robot_startup이 실행됩니다. 계정 공란은 로컬 서비스나 SSH를 시작하기 전에 거절됩니다. 모드별 명령 확인

로봇에서 “No executable found”가 나와요

로봇에도 새 코드를 배포해 cobot_pinky_patrol을 재빌드해야 합니다. 관제만 빌드하면 로봇의 새 실행기가 생기지 않습니다. 원격에서 source하는 경로가 /ws/kernel-robot-repo-4/install/setup.bash인지 확인합니다.

pinky_bringup 또는 pinky_navigation 패키지를 찾지 못해요

vendor workspace의 install/setup.bash 절대 경로를 underlay_setups에 넣습니다. 원격 환경에서 ROS → vendor → 패트롤 workspace 순서로 source합니다. 터미널에서 자동 적용하던 DDS 환경도 environment에 명시합니다.

지도 YAML은 있는데 지도 이미지가 없다고 나와요

~/는 SSH 계정의 로봇 HOME입니다. YAML의 image: 경로를 확인합니다. 상대 경로는 실제 YAML 파일이 있는 디렉터리 기준이며, 원격 기동기는 지도와 이미지를 확인한 뒤 프로세스를 시작합니다.

5초가 지났는데 다음 단계로 넘어가지 않아요

5초는 최소 간격입니다. 센서 메시지 또는 Nav2 활성 상태 검사가 통과해야 넘어갑니다. readiness_topics가 장비 토픽과 맞는지, amcl·bt_navigator가 active인지 확인합니다. 각 단계 제한은 기본 90초입니다.

SSH 인증·호스트 키 오류가 나와요

실제 ssh_user, 키 인증, 사전에 확인·등록된 호스트 키를 확인합니다. 기동기는 비대화식 연결을 사용하고 호스트 키 검사를 끄지 않습니다. YAML에는 비밀번호나 개인키 본문을 저장하지 않습니다.

YAML을 수정했는데 이전 설정으로 실행돼요

기본 launch와 명령 선택기는 설치 경로의 YAML을 읽습니다. 소스 변경 후 재빌드하고 install/setup.bash를 source하거나, launch의 config:=/절대/경로/fleet_startup.yaml 또는 CLI의 --config로 사용할 파일을 명시합니다. 패트롤의 현장·로봇 설정은 각 로봇에도 배포해야 합니다.

Ctrl+C로 종료하면 로봇 쪽도 끝나나요?

관제는 소유한 서비스와 SSH 세션을 역순 종료하고, 로봇 기동기는 HUP/TERM 처리로 자신이 시작한 launch들을 정리합니다. 다른 도구가 실행한 프로세스를 임의로 종료하지 않습니다. 강제 전원 종료·네트워크 단절의 즉시 물리 정지를 보장하는 기능은 아닙니다.

업무가 UNKNOWN이고 다음 작업이 거절돼요

작업 종료가 확인되지 않아 로봇 예약을 유지하는 상태입니다. 같은 ID의 지연 최종 응답으로 해소되거나, 현장에서 정지·작업 종료를 확인한 뒤 fleet_resolve_unknown으로 한 건을 수동 해제합니다. 운영 CLI 안내

BT 화면이 로봇 움직임에 따라 자동 갱신되지 않아요

이 HTML은 기록 재생 문서입니다. 실제 관제 DB에서 fleet_bt_trace로 JSON을 내보내고 파일을 선택합니다. 기본 데이터는 격리 시험 이력이며 현재 로봇 상태가 아닙니다.

대안: Docker로 관제 서비스 실행

Docker 구성은 관제 서비스와 선택형 브로커를 실행합니다. 로봇 SSH 기동은 포함하지 않습니다. 이미 Docker로 관제 서비스를 켰다면 위 명령 선택기에서 로봇만을 선택합니다.

관제 PC의 ROS source → venv 생성 → pip 설치 → colcon 빌드를 이미지 빌드로 옮깁니다. Linux Docker Engine + Compose 플러그인이 있으면 호스트에 ROS·Python 라이브러리를 설치하지 않아도 됩니다. Pinky의 Nav2·순찰 실행기는 각 로봇에 배포하는 기존 절차를 유지합니다.

처음 한 번 · 이미지 빌드

cd src/cobot_navigation
bash cobot_fleet_control/config/docker/fleet_docker.sh build

현재 코드를 이미지 안에 복사하고 세 관제 패키지를 빌드합니다. 이 단계에서는 실제 ROS 프로세스를 실행하지 않습니다.

로컬 브로커는 호스트 loopback 1883 포트를 사용하는 개발용입니다. 기존 브로커가 있으면 up을 사용합니다. 기존 호스트의 관제·브릿지·zone_manager와 중복 실행하지 않으며, 작업·구역 점유를 정리한 뒤 교체합니다. 컨테이너 시작 순서는 ROS·MQTT 연결 완료를 보장하지 않으므로 로그·실제 이벤트도 확인합니다.

대상고정·보존 방법
ROS Jazzy 기반 이미지공식 registry에서 확인한 manifest digest로 고정. Ubuntu 24.04·Python 3.12 계열 사용.
Python 의존성py_trees 2.2.3, paho-mqtt 2.1.0, pydot 2.0.0, pyparsing 3.1.4. pip 25.0.1·setuptools 75.8.0까지 wheel SHA-256으로 고정.
MQTT 브로커선택형 Mosquitto 2.0.22 이미지 digest 고정. 외부 브로커 주소는 실행 환경에서 지정.
관제 코드와 출처코드를 이미지에 복사하며 호스트 소스는 마운트하지 않음. Git revision·미커밋 변경 여부·설치 버전 목록 기록.
SQLitefleet-data named volume의 /var/lib/cobot/fleet_control.sqlite3. 기본 down·컨테이너 교체 후 보존. 기존 호스트 DB 자동 이전은 하지 않음.
배포할 때는 검증한 완성 이미지 ID/digest를 재사용합니다. 추가 apt 패키지는 빌드 시점 저장소에서 받으므로 날짜가 다른 재빌드까지 완전히 같다고 보장하지 않습니다. 이미지 태그·베이스 digest·Python lock·실제 설치 내역을 함께 관리합니다.

이번에 추가

로봇 · Nav2 / BehaviorTree.CPP

Nav2 BT Navigator는 BT XML을 읽어 BehaviorTree.CPP로 실행합니다. 로봇 실행기는 비동기 ActionClient로 Nav2를 호출합니다. Nav2의 BT XML이나 플러그인을 새로 배포하지 않습니다. 로봇의 실제 XML 선택은 현장 설정 확인이 필요합니다. Jazzy 공식 설명

경로담기는 데이터확인하는 의미
cobot/fleet/commands업무 JSON · QoS 1 · retain=false실행 요청. 브로커 ACK은 작업 성공을 의미하지 않음

commands정규화된 입력 · 로봇 · 최신 업무 상태중복 방지와 서버 재시작 후 미확정 작업 확인

UNKNOWN은 실패나 정지 확정이 아닙니다. 응답 시간 초과·서버 재시작·전달 예외에는 로봇 예약을 유지합니다. 실제 지연 최종 응답이 오면 해제합니다. 응답이 영구 유실된 경우 현장 확인 후 별도 조정이 필요합니다. 물리 동작의 exactly-once는 보장하지 않습니다.

정지와 취소를 디버깅할 때

stop / emergency_stop 수신
 → PatrolController.stop(): CANCELING 등록, cancel() 요청, 즉시 반환
 → 목표 접수 전이라면 _cancel_requested=True로 기억
 → _accepted()에서 접수 확인 후 cancel_goal_async()
 → _cancelled(): 취소 요청의 응답만 확인 — busy를 해제하지 않음
 → _finished(): 원래 액션이 실제로 종료되었을 때 busy=False
 → _stop_after_cancel()
     stop + 구역 보유: EXIT 이동 완료 후 토큰 반납 → STOPPED
     emergency_stop: 추가 이동 없이 토큰 유지 → STOPPED

취소가 거절되거나 결과 통신이 끊기면 아직 끝나지 않은 액션을 새 목표로 덮어쓰지 않습니다. busy를 유지하고 관제는 시간 초과 후 UNKNOWN으로 남길 수 있습니다. 비상정지는 소프트웨어 요청이며 하드웨어 비상정지를 대신하지 않습니다.

아래 트리는 실제 py_trees 실행에서 수집한 스냅샷을 재생합니다. 기본 이력은 가짜 로봇·임시 SQLite를 사용한 격리 실행이며 실물 데이터가 아닙니다. 노드의 상태 색과 이번 tick 방문 여부를 나눠 보세요.

첫 tick: 전달 SUCCESS → 대기 RUNNING. 다음 tick: 전달은 SUCCESS를 유지하지만 다시 실행되지 않습니다. 종료 tick: 대기와 루트가 SUCCESS/FAILURE로 바뀝니다. 타임아웃의 루트 FAILURE는 업무 UNKNOWN과 함께 표시합니다.

파일은 브라우저 안에서만 읽습니다. MQTT 실시간 구독은 하지 않습니다. 스냅샷은 상태 또는 방문 경로가 바뀔 때만 기록하므로 tick 번호가 건너뛸 수 있습니다.

INVALID · 미실행/무효RUNNINGSUCCESSFAILURE밝은 외곽선 = 이번 tick 방문

트리 상태·방문 경로의 원본은 공식 SnapshotVisitor와 각 Behaviour의 status입니다. 트리 구조는 해당 실행의 children 관계로 그립니다.
