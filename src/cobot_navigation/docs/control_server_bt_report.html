로컬 브로커는 호스트 loopback 1883 포트를 사용하는 개발용입니다. 기존 브로커가 있으면 up을 사용합니다. 기존 호스트의 관제·브릿지·zone_manager와 중복 실행하지 않으며, 작업·구역 점유를 정리한 뒤 교체합니다. 컨테이너 시작 순서는 ROS·MQTT 연결 완료를 보장하지 않으므로 로그·실제 이벤트도 확인합니다.

대상고정·보존 방법
ROS Jazzy 기반 이미지공식 registry에서 확인한 manifest digest로 고정. Ubuntu 24.04·Python 3.12 계열 사용.
Python 의존성py_trees 2.2.3, paho-mqtt 2.1.0, pydot 2.0.0, pyparsing 3.1.4. pip 25.0.1·setuptools 75.8.0까지 wheel SHA-256으로 고정.
MQTT 브로커선택형 Mosquitto 2.0.22 이미지 digest 고정. 외부 브로커 주소는 실행 환경에서 지정.
관제 코드와 출처코드를 이미지에 복사하며 호스트 소스는 마운트하지 않음. Git revision·미커밋 변경 여부·설치 버전 목록 기록.
SQLitefleet-data named volume의 /var/lib/cobot/fleet_control.sqlite3. 기본 down·컨테이너 교체 후 보존. 기존 호스트 DB 자동 이전은 하지 않음.
배포할 때는 검증한 완성 이미지 ID/digest를 재사용합니다. 추가 apt 패키지는 빌드 시점 저장소에서 받으므로 날짜가 다른 재빌드까지 완전히 같다고 보장하지 않습니다. 이미지 태그·베이스 digest·Python lock·실제 설치 내역을 함께 관리합니다.

3. MQTT 브로커 준비

기본 연결 주소는 localhost:1883입니다. 이미 브로커가 있으면 그대로 사용합니다. 관제 PC에 Mosquitto가 설치돼 있고 1883 포트가 비어 있다면, 개발용 로컬 브로커를 별도 터미널에서 다음처럼 실행할 수 있습니다.

mosquitto -p 1883 -v

다른 서버를 쓰면 fleet_control.yaml의 mqtt_host·mqtt_port를 맞춥니다. 계정·TLS는 COBOT_MQTT_USERNAME·COBOT_MQTT_PASSWORD·COBOT_MQTT_CA 환경변수를 사용합니다. 브로커는 관제 launch가 자동으로 띄우지 않습니다.

6. 상태를 구독한 뒤 UI 또는 MQTT로 명령 전송

현재 UI 버튼의 MQTT 발행 연결은 별도 구현 대상입니다. Mosquitto 클라이언트가 설치된 환경에서는 아래 명령으로 입력·결과를 확인할 수 있습니다. 다른 브로커를 쓴다면 호스트·포트·인증 옵션도 맞춥니다.

# 별도 모니터 터미널: 접수 결과·업무 상태·로봇 상태·BT 스냅샷
mosquitto_sub -h localhost -p 1883 -q 1 -v \
  -t 'cobot/fleet/receipts' -t 'cobot/fleet/events'

아래 발행 명령은 실제 이동 요청입니다. 로봇·주변·지점 좌표를 확인한 뒤 실행합니다. 새 작업에는 새 command_id를 사용하고 동일 요청 재전송에는 기존 ID를 유지합니다. retain 옵션은 사용하지 않습니다.

mosquitto_pub -h localhost -p 1883 -q 1 \
  -t 'cobot/fleet/commands' \
  -m '{"command_id":"job-run-001","robot_id":"pinky1","operation":"goto","points":["P1"],"timeout_sec":300}'

수신 확인: ACCEPTED → RUNNING → SUCCEEDED/FAILED 또는 UNKNOWN. 이벤트 중 type=bt_snapshot에는 노드 상태와 이번 tick 방문 여부가 들어갑니다. MQTT 연결 확인과 로봇 주행 성공은 따로 확인합니다.

7. 방금 실행한 작업의 실제 BT를 HTML에서 확인

관제 PC의 환경을 불러온 별도 터미널에서, 위 명령 ID로 이력을 내보냅니다. 명령이 실행 중이어도 현재까지 기록된 스냅샷을 읽을 수 있습니다.

ros2 run cobot_fleet_control fleet_bt_trace \
  --db ~/.cobot/fleet_control.sqlite3 \
  --command-id job-run-001 \
  --output /tmp/bt_trace.json
  1. 이 HTML의 BT 실행 시각화로 이동합니다.
  2. 관제 DB에서 내보낸 실행 이력 JSON 열기에서 /tmp/bt_trace.json을 선택합니다.
  3. 출처가 가져온 DB 기록으로 바뀌었는지 확인합니다. 초기의 격리 시험 데이터와 구분됩니다.
  4. 이전/다음·슬라이더로 노드 색과 방문 여부를 확인합니다. 정상 실행에서는 전달 노드는 한 번만 실행되고 대기 노드가 계속 방문됩니다.

이 화면은 가져온 파일 시점의 기록입니다. 이후 상태를 보려면 다시 내보내고 파일을 다시 선택합니다. 스냅샷이 0개라면 command_id·DB 경로·명령 접수 여부·새 패키지 배포 여부를 확인합니다. 관측 대상은 관제 Python BT이며 로봇 Nav2 내부 BT는 별도 계측 대상입니다.

명령은 goto:P1 같은 String어떤 UI 요청의 결과인지 연결할 ID가 없음기존 String 토픽 안에 JSON 봉투와 명령 ID 추가
로봇 내부에서 명령 분기·Nav2·LED·유휴 복귀·구역 처리업무 정책과 장비 실행 경계가 흐림관제 BT·업무 서비스·저장소·통신 어댑터 분리. 기존 장비 실행 정책은 단계적으로 유지
MQTT·DB 경로 없음요청 이력, 재전송, 서버 재시작 시 작업 추적이 어려움Paho MQTT + SQLite + 영속 outbox 구현
로봇이 DONE을 보낸 뒤 LED 등 정리 작업 수행관제가 곧바로 다음 명령을 보내면 로봇이 작업 중으로 무시 가능액션 종료·필요한 구역 반납 후 task_finished=true 최종 응답

별도 확인 사항: zone_gate_client 직접 import, 강제 토큰 만료, 임시 지점 좌표, 대기 슬롯 중첩 가능성은 기존 구조에 남습니다. 이번 작업에서 해당 물리 정책을 바꾸지 않았습니다.

node         MQTT 큐 / ROS 입출력 / tick

DB는 교체할 수 있는 어댑터

현재도 실제 파일 SQLite에 기록합니다. 향후 서버 DB가 정해지면 저장소 경계를 구현하고 상태 변경과 outbox 삽입을 같은 트랜잭션으로 묶습니다.

PostgreSQL 등 외부 DB 연결·마이그레이션은 아직 구현하지 않았습니다. 다중 서버에는 원자적 로봇 예약·고유 제약·리더 선출이 추가로 필요합니다.

03. ROS 2 BT와 Python BT의 역할

이번에 추가

관제 · py_trees 2.2.3

 │   ├─ DB: RUNNING 기록

대기 노드는 즉시 RUNNING을 반환합니다. memory Sequence가 대기 노드에서 재개하므로 tick마다 이동 명령을 다시 보내지 않습니다. 실제 구현은 이 두 단계이며 충전·검사·복합 작업 트리는 후속 확장입니다. 공식 Sequence 설명

기존 실행 체계 재사용

로봇 · Nav2 / BehaviorTree.CPP

공통 순찰 실행기
 └─ 비동기 ActionClient
     └─ NavigateToPose
         └─ Nav2 BT Navigator
             ├─ 경로 계산
             ├─ 경로 추종
             └─ Nav2 복구 동작

Nav2 BT Navigator는 BT XML을 읽어 BehaviorTree.CPP로 실행합니다. 로봇 실행기는 비동기 ActionClient로 Nav2를 호출합니다. Nav2의 BT XML이나 플러그인을 새로 배포하지 않습니다. 로봇의 실제 XML 선택은 현장 설정 확인이 필요합니다. Jazzy 공식 설명

BehaviorTree.ROS2는 C++ ROS 액션·서비스 노드가 필요한 향후 대안입니다. 현재는 Python 관제와 기존 Nav2가 이미 있어 중복 실행 엔진을 추가하지 않았습니다.

{
  "command_id": "job-20261031-001",

위 값은 계약 설명을 위한 예시입니다. status.time은 로봇 보고 시각, recorded_at은 관제 기록 시각입니다. MQTT 이벤트는 중복될 수 있어 UI가 event_id로 제거해야 합니다. 로봇 원문 상태도 type=robot_status 이벤트와 DB 최신 상태로 보관합니다.

경로담기는 데이터확인하는 의미
cobot/fleet/commands업무 JSON · QoS 1 · retain=false실행 요청. 브로커 ACK은 작업 성공을 의미하지 않음
cobot/fleet/receipts접수/중복 현재 상태 또는 REJECTED편의 알림. 거절 내역은 현재 영속 저장하지 않음
/pinkyN/patrol_status로봇 실행 상태 · 명령 ID · 종료 여부중간 DONE과 실제 작업 정리 종료를 구분
commands정규화된 입력 · 로봇 · 최신 업무 상태중복 방지와 서버 재시작 후 미확정 작업 확인
robot_status로봇별 최신 상태 원문과 수신 시각UI 현재 상태 조회 어댑터의 데이터 원본
outbox → cobot/fleet/events명령 상태·로봇 상태·BT 스냅샷 이벤트와 고유 event_id상태 변경과 통지 예약을 원자 기록. PUBACK 후 발행 완료 처리
UNKNOWN은 실패나 정지 확정이 아닙니다. 응답 시간 초과·서버 재시작·전달 예외에는 로봇 예약을 유지합니다. 실제 지연 최종 응답이 오면 해제합니다. 응답이 영구 유실된 경우 현장 확인 후 별도 조정이 필요합니다. 물리 동작의 exactly-once는 보장하지 않습니다.

한 명령의 콜백 흐름

MQTT _message() → 수신 큐 → _consume()
 → Command.parse() → FleetService.submit() → DB ACCEPTED
 → FleetService.tick() → Dispatch.update() → ROS patrol_cmd
 → PinkyPatrolNode._cmd_cb() → PatrolController.submit()
 → PREPARING: 라이프사이클·초기화 준비, 각 콜백은 즉시 반환
 → NEXT: 다음 단계 선택
     gate → QUEUEING: 허가·슬롯 확인, 필요하면 슬롯 액션 요청
     move/exit/home → NAVIGATING: 액션 접수·종료 콜백 대기
 → AsyncNavigation._finished()가 최종 결과 등록
 → PatrolController._move_tick()가 결과 소비·다음 단계 선택
 → _finish(): task_finished=true 상태 발행
 → FleetService.on_status() → AwaitResult.update() → DB 결과·MQTT 이벤트

정지와 취소를 디버깅할 때

stop / emergency_stop 수신
 → PatrolController.stop(): CANCELING 등록, cancel() 요청, 즉시 반환
 → 목표 접수 전이라면 _cancel_requested=True로 기억
 → _accepted()에서 접수 확인 후 cancel_goal_async()
 → _cancelled(): 취소 요청의 응답만 확인 — busy를 해제하지 않음
 → _finished(): 원래 액션이 실제로 종료되었을 때 busy=False
 → _stop_after_cancel()
     stop + 구역 보유: EXIT 이동 완료 후 토큰 반납 → STOPPED
     emergency_stop: 추가 이동 없이 토큰 유지 → STOPPED

취소가 거절되거나 결과 통신이 끊기면 아직 끝나지 않은 액션을 새 목표로 덮어쓰지 않습니다. busy를 유지하고 관제는 시간 초과 후 UNKNOWN으로 남길 수 있습니다. 비상정지는 소프트웨어 요청이며 하드웨어 비상정지를 대신하지 않습니다.

증상별 중단점과 확인 항목

증상중단점을 둘 함수확인할 데이터·판단
UI 명령이 관제에 안 들어옴FleetControlNode._connect / _message / _consume브로커 주소·포트·인증, 연결 결과, commands 토픽, QoS 1, retain=false, inbox 포화. UI 버튼의 MQTT 발행 연결도 확인한다.
접수는 됐지만 ROS 명령이 안 나감FleetService.submit / tick, Dispatch.update, FleetControlNode.sendcommand_id 중복, repository.busy(), active 등록, ROS_DOMAIN_ID와 브릿지 토픽. 구독자 수가 있어도 브릿지 너머 실제 로봇 도착까지 보장하지는 않는다.
STARTING에서 이동하지 않음PinkyPatrolNode._poll_lifecycle / _state_received / _advance_preparation / _readyamcl·bt_navigator가 active인지, action server 발견 여부, _restore_stage, initialpose 구독자, 준비 제한 시간. restore_pose 설정과 저장 좌표 파일도 확인한다.
목표 접수 후 결과가 안 옴AsyncNavigation._accepted / _finished, PatrolController._move_tickhandle.accepted, get_result_async의 완료, GoalStatus, busy·fault. 내부 Future.result()는 완료 콜백 안에서만 읽는다.
구역 대기에서 멈춤PatrolController._queue_tick, ZoneGateClient._on_grant / _on_slot / resend_if_due구역·robot_id·토큰 일치, current_slot, grant 수신, 매니저 대기열, 재요청 시각. 슬롯 목표 변경 때 이전 액션 종료를 기다리는 중인지 확인한다.
stop을 보냈지만 안 끝남PatrolController.stop / _stop_after_cancel, AsyncNavigation.cancel / _cancelled / _finishedphase=CANCELING, 접수 전 취소 플래그, 취소 거절·통신 예외, 원래 액션 최종 결과. cancel ACK만 보고 완료로 처리하면 안 된다.
출구로 갔는데 토큰이 유지됨PatrolController._move_tick, ZoneGateClient.notify_exit, ZoneManagerNode._on_exitexit 목표의 실제 SUCCEEDED 여부, held_zone, zone 접두·robot_id, notify_exit 전달. 출구 실패라면 토큰 유지가 의도된 동작이다.
다른 명령의 결과가 섞임PatrolController.submit / _reject / _finish, AsyncNavigation._feedback / _finished, FleetService.on_statuscommand_id·robot_id와 액션 _generation 확인. 새 명령의 busy 거절이 기존 명령의 종료로 기록되지 않아야 한다.
LED가 안 바뀌지만 이동은 됨PinkyPatrolNode._set_led / _advance_led / _led_done별도 LED 서버, service_is_ready(), _led_future, 원하는 색과 _led_sent. LED 지연은 주행 콜백을 막지 않는다.
DB에는 있는데 UI 결과가 안 보임SqliteRepository.transition / pending / acknowledge, FleetControlNode._tick실제 db_path, outbox payload, MQTT 연결과 PUBACK, UI의 events 구독·event_id 중복 제거. PUBACK은 UI 표시 완료가 아니다.
BT 시각화가 안 바뀜TreeTrace.capture, export_traces, HTML 파일 선택명령 ID·DB 경로·파일 생성 시각, snapshot의 phase/tick/nodes/visited. 같은 대기 상태는 저장을 생략하고 HTML은 가져온 파일을 재생한다.

실제 BT 실행 상태 시각화

아래 트리는 실제 py_trees 실행에서 수집한 스냅샷을 재생합니다. 기본 이력은 가짜 로봇·임시 SQLite를 사용한 격리 실행이며 실물 데이터가 아닙니다. 노드의 상태 색과 이번 tick 방문 여부를 나눠 보세요.

첫 tick: 전달 SUCCESS → 대기 RUNNING. 다음 tick: 전달은 SUCCESS를 유지하지만 다시 실행되지 않습니다. 종료 tick: 대기와 루트가 SUCCESS/FAILURE로 바뀝니다. 타임아웃의 루트 FAILURE는 업무 UNKNOWN과 함께 표시합니다.

파일은 브라우저 안에서만 읽습니다. MQTT 실시간 구독은 하지 않습니다. 스냅샷은 상태 또는 방문 경로가 바뀔 때만 기록하므로 tick 번호가 건너뛸 수 있습니다.

INVALID · 미실행/무효RUNNINGSUCCESSFAILURE밝은 외곽선 = 이번 tick 방문

트리 상태·방문 경로의 원본은 공식 SnapshotVisitor와 각 Behaviour의 status입니다. 트리 구조는 해당 실행의 children 관계로 그립니다.

      08. 도입 순서와 남은 범위
      

      1. 로봇 실행기부터 새 버전으로 배포: 기존 실행 이름·YAML은 유지. 신규 JSON 명령과 최종 응답을 이해해야 합니다.
      2. 브로커 준비: TLS·ACL·계정과 영속 저장을 구성합니다. 브라우저 MQTT 직접 연결에는 WSS 리스너가 필요합니다.
      3. 관제 1개 실행: DB 저장 경로와 기존 도메인 브릿지·zone_manager를 확인합니다. 패키지의 실행 안내를 따릅니다.
      4. UI 연결: 명령 ID 생성, receipts 표시, events의 event_id 중복 제거, 업무 상태와 물리 상태를 나눠 표시합니다.
      5. 서버 DB·운영 API 확장: DB 어댑터, 과거 이벤트 조회, UNKNOWN 현장 확인·해제, MQTT 취소/선점 계약을 추가합니다.
      6. 업무 정책 이전: 현재 로봇에 남은 유휴 복귀·구역 실행 절차를 관제 BT로 옮길지 결정합니다. 현재 로봇 단계는 단일 executor의 비동기 상태 기계로 동작합니다. 로컬 정지·주행 보호는 로봇에서 계속 처리합니다.
      

      이번 구현의 경계
      단일 서버와 명령 단위 BT가 구현 범위입니다. UI 제품 화면, 외부 운영 DB, 복합 업무·충전·다중 서버 리더 선출, 조회 HTTP API는 포함하지 않습니다. 이 HTML은 배포용 관제 UI가 아니라 독립 리포트입니다.
      

      물리 동작·데이터 신뢰성의 남은 항목
      ROS String 전달과 DB는 하나의 트랜잭션이 아닙니다. 관제 재시작 때 자동 재전송하지 않고 UNKNOWN으로 남깁니다. 로봇 재시작 후의 영속 명령 중복 제거·완료 응답 재전송·하트비트는 후속 계약입니다. 큐 포화 시 접수하지 않고 오류를 기록하며, 지속 세션의 미확인 메시지는 브로커 설정·재접속에 의존합니다. UI 수신 ACK은 현재 구현하지 않았으므로 MQTT PUBACK과 UI 화면 반영은 서로 다릅니다.
      

      기존 구역·좌표 정책의 남은 항목
      유휴 120초 자동 복귀, max_hold_sec 토큰 강제 해제, 패키지 간 zone_gate_client 직접 import, 임시 좌표와 대기 슬롯 중첩 가능성은 별도 검증·변경 대상입니다. 실제 장비·도메인 브릿지·현장 지도에서의 주행은 이번 격리 테스트가 보증하지 않습니다.
