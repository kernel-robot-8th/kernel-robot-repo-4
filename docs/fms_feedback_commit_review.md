# 웹 메모칸이 커밋에 주는 영향

**메모를 적는 것만으로 Git 커밋이나 GitHub 업로드가 생기지는 않는다. 다만 저장 파일이 바뀌므로 나중에 기능 수정과 섞어 커밋할 수 있다.**

## 확인한 동작

| 사용 방식 | 저장되는 곳 | 커밋 영향 |
|---|---|---|
| `npm run dev`의 메모 등록·삭제 | 실행한 작업 폴더의 `src/cobot_gui/web/src/data/fms_feedback.json`과 브라우저 저장소 | Git 관리 파일이 수정됨. 자동 커밋·push 없음. |
| 메모 내보내기 | 사용자가 내려받는 Markdown 파일 | 내려받기만 하면 저장소는 바뀌지 않음. |
| `npm run build` 후 `npm run preview` | 브라우저 저장소는 사용할 수 있지만 메모 저장 API는 없음 | Git 파일 영속 저장을 보장하지 않음. |

메모 기능은 main의 `54eba2f`(패널), `ffb8ba0`(파일 저장 API), `a3ce4f1`(타입 오류 수정)에 들어 있다. 코드의 'Git-backed'는 **Git이 관리하는 파일에 쓴다**는 뜻이다. GitHub 동기화 기능은 구현돼 있지 않다.

## PR #7·#8과의 관계

- PR #7과 #8은 같은 main 기준에서 출발해 메모 기능을 이미 포함한다.
- 두 PR 모두 메모 패널·저장 API·메모 JSON을 수정하지 않았다. PR #8은 사용 규칙과 이 확인 문서만 추가한다.
- 따라서 두 PR 때문에 기존 메모 코드가 없어지는 변경은 없다. 실제 사용자 메모를 어느 브랜치에서 저장했는지는 별도다.
- 다른 브랜치·다른 작업 폴더는 메모 파일도 따로 갖는다. 브랜치 전환·병합 전에 저장 파일을 확인하고 필요한 메모를 내보낸다.

## 팀이 지킬 것

1. 기능을 커밋할 때는 필요한 파일만 선택한다. 메모까지 의도 없이 한꺼번에 올리지 않는다.
2. 공유할 메모는 검토 후 메모 데이터만 별도 커밋·PR로 올린다. 개인정보·비밀값을 적지 않는다.
3. 메모칸은 의견을 모으는 곳이다. 담당·규칙 확정은 검토를 거쳐 정식 문서에 반영한다.

## 남아 있는 한계

- 서버 저장이 실패해도 화면에 등록된 것처럼 보일 수 있다. 현재 버튼 문구만으로 파일 저장 성공을 판단하면 안 된다.
- 서버에서 받은 목록이 브라우저 목록을 교체한다. 브라우저에만 있던 메모를 자동으로 합쳐 보존하는 기능은 없다.
- 일반 정적 배포에도 메모를 영속 저장하려면 별도 API가 필요하다. 여러 사람이 동시에 사용할 때의 저장 충돌도 추가 검증 대상이다.

## 이번 확인 범위

main `a3ce4f1`의 웹 소스를 독립 복사본에서 빌드하고 시험했다. 실제 사용자 메모와 원본 저장소는 바꾸지 않았다.

- 등록 HTTP 201, 조회·삭제 정상. 등록 시 Git 관리 JSON만 변경되고 HEAD는 그대로였다.
- 정적 미리보기의 `/api/feedback`은 JSON이 아닌 HTML을 반환해 저장 API가 없음을 확인했다.
- 시험 서버를 종료하고 복사본의 메모 파일을 원래대로 복구했다.
- 결과: [확인 기록](evidence/feedback-commit-check-20261024.json). 실제 배포 서버의 저장 상태를 확인한 결과는 아니다.
