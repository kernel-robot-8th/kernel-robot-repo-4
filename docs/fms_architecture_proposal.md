## 2. 일반적인 다중 로봇 통신 방식

관제 ↔ 로봇 구간을 "명령 보내기 + 상태로 확인" 토픽으로 만드는 것은 흔한 방식이다.

- 물류 로봇 관제 표준 VDA 5050도 MQTT로 명령(order) 토픽과 상태(state) 토픽을 나누고 ID·순번으로 맞춘다. 현재 `patrol_cmd`/`patrol_status`와 `command_id`·순번 구조가 이와 비슷하다.
- 와이파이처럼 끊기기 쉬운 망에서는 ROS 액션·서비스를 원격으로 직접 거는 것보다 토픽 방식이 튼튼하다. 액션은 연결이 끊기면 결과 상태가 애매해진다.
- 보통 로봇 안에서는 Nav2 액션을, 관제 ↔ 로봇 구간은 토픽(또는 MQTT·HTTP)을 쓴다.

| 방법 | 쓰임 | 특징 |
|---|---|---|
| 같은 도메인 + 네임스페이스(`/pinky1/...`) | 소규모에서 가장 흔함 | 가장 간단하다. 대수가 늘면 DDS 탐색 트래픽이 많아진다. |
| Zenoh (`rmw_zenoh`, zenoh 브릿지) | Jazzy부터 늘어나는 추세 | 와이파이·원격 연결에 강하고 탐색 트래픽이 적다. |
| Fast DDS Discovery Server | 꽤 쓰임 | 탐색 트래픽을 줄인다. |
| Open-RMF 등 + HTTP/MQTT | 실제 현장 관제에서 흔함 | 관제 ↔ 로봇을 ROS 밖의 방식으로 잇는다. |
| domain_bridge (현재 방식) | 상대적으로 적음 | 도메인 격리용이다. 마지막 릴리스가 0.5.0(2022)이다. 넘길 토픽을 YAML에 하나씩 적어야 해서 토픽이 늘 때마다 로봇 3대분 설정을 고쳐야 한다. |

### 2-1. 개발용·운영용 화면 분리

- 실제 현장 관제는 보통 운영 화면과 엔지니어 화면을 역할(권한)로 나누고, 개발·디버그 도구(RViz, Foxglove, BT 뷰어 등)는 따로 둔다.
- 운영 화면을 별도 웹으로 만들어도 같은 API 서버와 공통 JS를 쓰면 두 벌이 아니다. 서버·명령 경로를 따로 만들 때 두 벌이 된다.
- 개발 기능 차단은 화면에서 숨기는 것이 아니라 서버에서 한다. 현재 코드는 이렇게 되어 있다.

## 3. 목표 구조 (처음부터 짠다면)

현재 코드와 팀 규칙을 고려하지 않고, 이 프로젝트 규모(핑키 3대, 팔 2대, 비전, 배송 시나리오)에 맞춰 짠 구조다.

### 3-1. 전체 구조

```
 ┌──────────────── 화면 (브라우저) ────────────────┐
 │ 운영 화면        엔지니어 화면        개발 도구          │
 │ (주문·예외 처리) (수동 이동·보정)     (Foxglove, BT 뷰어) │
 └───────┬──────────────┬───────────────────────┘
         │ HTTP + WebSocket (로그인·역할 확인)   ※ 개발 도구는 ROS에 직접 붙음
 ┌───────▼───────────────────────────────────────┐
 │ 중앙 관제 서버 (프로세스 1개, 상태의 정본은 여기 하나)    │
 │  ├ API 계층: REST/WS, 인증, 권한, 감사 기록              │
 │  ├ 주문 관리: 접수, 재고, 상태                          │
 │  ├ 배정: 어떤 로봇이 어떤 주문을                        │
 │  ├ 시나리오 실행: 주문별 BT                             │
 │  ├ 교통 관리: 구역 토큰, 통로 예약                       │
 │  ├ 예외 큐: 멈춤, 결과 모름, 사람 확인이 필요한 것         │
 │  └ DB: 주문, 이벤트, 감사 기록                          │
 └───────┬──────────────────────┬────────────────┘
         │ ROS2 정식 msg (Zenoh)   │ ROS2 정식 msg/action (유선)
 ┌───────▼────────┐       ┌───────▼──────────────┐
 │ 로봇 에이전트 ×3  │       │ 작업장 에이전트 ×2       │
 │ Nav2, 로컬 안전   │       │ 팔 + 비전, 같은 인터페이스 │
 └────────────────┘       └──────────────────────┘
        하드웨어 비상정지: 소프트웨어와 분리된 별도 회로
```

### 3-2. 핵심 원칙

1. **중앙 서버는 프로세스 하나로**: 웹 → ROS 토픽(JSON) → fleet으로 건너가지 않고, API 계층이 관제 로직을 직접 호출한다. 요청·응답 토픽을 맞추는 코드와 웹의 모드 짐작이 사라진다. ROS는 로봇·장치 쪽에만 쓴다.
2. **로봇 통신은 "명령 + 상태" 토픽, 형식은 정식 msg**: VDA 5050처럼 `RobotOrder`를 내리고 `RobotState`를 올린다. ID·순번을 붙인다. 와이파이 구간이라 원격 액션은 쓰지 않는다. `String`+JSON 대신 `cobot_interfaces`의 정식 msg를 쓴다.
3. **도메인 브릿지 대신 Zenoh**: `rmw_zenoh`(Jazzy 지원)와 로봇별 네임스페이스를 쓴다. 와이파이에 강하고, 토픽마다 YAML에 적을 필요가 없다.
4. **팔·비전은 "작업장 에이전트" 하나의 인터페이스로**: 중앙은 `ExecuteStep(step_id, 종류, 대상)`을 보내고 결과(성공, 재시도 가능 여부, 증거)를 받는다. 팔과 비전의 협력은 작업장 에이전트 안에서 처리한다. 유선 구간이라 액션을 써도 된다. 가짜 작업장(mock)도 같은 인터페이스로 만들어 시뮬레이션에서 시나리오 전체를 끝까지 돌린다.
5. **안전은 로봇 쪽에서 먼저**: 생존 신호는 받는 쪽 자기 시계로만 센다(마지막 수신 후 경과 시간). PC 간 시계는 비교하지 않고, NTP는 로그 정렬용으로만 쓴다. 끊기면 로봇이 스스로 멈춘다. 하드웨어 비상정지는 소프트웨어와 무관한 별도 회로로 둔다.
6. **예외 처리는 "예외 큐" 한 곳에서**: 멈춤, 결과 모름, 잠금, 구역 안 정지를 모두 카드 하나로 만들고, 카드마다 안내형 복구 절차를 붙인다(예: 현장 확인 → 구역 이탈 허용 → 토큰 반납 → 재개). 파라미터·개별 버튼으로 흩어진 복구 방법을 한 곳으로 모은다.
7. **화면은 역할로 나누고, 권한은 서버가 검사**:
   - 운영 화면: 주문 접수, 진행 지도, 예외 큐, 수령 확인 (현장 운영자)
   - 엔지니어 화면: 로봇 수동 이동, 보정, 수동 명령 (로그인한 엔지니어)
   - 개발 도구: Foxglove, BT 뷰어 (현장 이미지에서는 기본으로 꺼 둠)
   - 운영·엔지니어 화면은 같은 API와 공통 JS를 쓴다. 웹 화면만 나누면 두 벌이 아니다. 누가 눌렀는지는 로그인 정보로 자동 기록한다.

### 3-3. 배포

- 관제 PC: 도커 compose 하나. 개발과 현장은 compose profile로 나눈다.
- 로봇·작업장 PC: systemd 서비스로 띄워 죽으면 자동으로 다시 켠다.
- 시뮬레이션: 가짜 로봇 + 가짜 작업장 + 실제 중앙 서버. 실물과 코드 차이가 없게 한다.

### 3-4. 현재와 다른 점

| 현재 | 추천 |
|---|---|
| 웹 → 토픽 JSON → fleet | API가 관제 로직을 직접 호출 (프로세스 하나) |
| `String` + JSON | 정식 msg |
| 도메인 브릿지 | Zenoh |
| 팔·비전 연결 없음 | 작업장 에이전트 인터페이스 하나 |
| 복구 방법이 흩어져 있음 | 예외 큐 + 안내형 복구 |
| 개발 화면만 있음 | 운영 화면과 엔지니어 화면, 역할·로그인 |
| SSH 스크립트로 기동 | systemd + compose |

### 3-5. 그대로 가져갈 것

주문별 BT, SQLite 실행 원장, 구역 토큰, 생존 신호와 세션·순번, 재시작 시 `UNKNOWN` 보류는 방향이 맞다. 전부 다시 짤 필요는 없고, 연결 방식과 화면 구조만 바꾸는 쪽이 현실적이다.
